    The workflow you'll practice

    From a fuzzy idea to a verified pull request

    AndThen chains a few skills into the Core Loop. Each step writes something the next step reads, and ends by printing the command to paste next.

    idea→ [clarify]→ plan→ exec-plan→ review --fix→ ship

    How much structure does the work need?

      Result

      Reads

      Pick a step on the rail, or use the arrow keys. Dashed steps are optional.

      Product and PRD

      PRODUCT.md and prd.md: two levels of requirements

      clarify writes both, at different levels. docs/PRODUCT.md describes the whole product, and there is one per project. prd.md describes one feature, and every feature gets its own, in its folder under docs/specs/.

      Product · one per project

      docs/PRODUCT.md

      What the product is, and how big what gets built may be. It sits above every PRD.

      • Holdsvision, target users, value propositions, non-goals and success metrics
      • Proportionalitystage, scale and standing technical non-goals
      • Written byclarify at product scope, or the first of clarify, decide, plan and architecture that needs the Proportionality facts
      • Read byevery skill that proposes something

      Long-lived. It changes when the stage or the scale changes.

      sizes

      Feature · one per feature

      prd.md

      What one feature must do, and how you know it is done. It lives in the feature’s folder, docs/specs/<feature>/.

      • Holdsthe problem, the requirements (FR1, FR2 …) with priority, what is in and out of scope, the MVP boundary, constraints and a decisions log
      • Written byclarify at feature scope, the default
      • Read byplan, which turns it into the FIS, and the outcome lens of review
      • Shippedship adds a Shipped line when it deletes the plan; an amendment through clarify removes it

      The PRD is anchored in the product. In the lab’s shared-lists PRD, email and notifications are out because docs/PRODUCT.md says prototype, one SQLite file and no external services. clarify drops or flags a capability those facts don’t carry, citing the anchor.

      How clarify picks the level

      Feature scope is the default and writes prd.md. Product scope applies when you name it (“clarify the product vision”), when the input is a file named PRODUCT*.md, or when the request talks about vision, positioning or product strategy. Then clarify writes the Product document instead of a PRD.

      Rule of thumb

      What the product is, and how big it may get, belongs in PRODUCT.md. What one feature must do, and how you know it is done, belongs in prd.md.

      Plan, stories and FIS

      How the plan, its stories and their specs fit together

      plan writes two kinds of file: one plan.json for the plan directory, and one FIS per story. A story is a slice of the work, and a FIS belongs to exactly one story. Tasks live only inside a FIS. Even a single feature gets a plan.json, with one story, S01.

      Requirements · optional

      prd.md

      What the work must do, from clarify. plan can also start from requirements you already have, a tracker item or a one-line request.

      plan

      One per plan directory

      plan.json

      The plan’s state. For each story: its dependencies (dependsOn), its status, which of its FIS tasks are done (completedTaskIds), and a pointer to its FIS. plan writes it; after that, the session building a story updates that story’s row. It says nothing about how to build anything. It lives on the branch. ship deletes it on your yes; kept, it gets a shipped marker as a record.

      • S01Lists have ownerss01-lists-have-owners.mddone
      • S02Share a listdepends on S01in-progress
      • S03Sort by due dateno dependenciesdone
      • S04Revoke a sharedepends on S02pending

      Mid-run: S01 and S03 are done, S02 is being built, and S04 waits for S02. A story becomes done only together with verified: when, and which check that actually ran proved it. You set skipped by hand.

      A story is a delivery piece, not an agile user story (“As a user I want…”). The FIS’s acceptance scenarios come closest to that.

      fis

      FIS · one per story

      s01-lists-have-owners.md

      The spec for one story: what to build, how each part is proved, and when it is done.

      • OC01 …Expected Outcomestwo to four, one sentence each
      • S01 …Acceptance ScenariosGiven, When, Then, each with its Proof
      • SC01 …Structural Criteriawhat the story’s diff must not break
      • TI01 …Implementation Tasksa state that must be true, with Verify (the check that proves it) and SATISFIES (the scenarios it moves forward)

      plan.json records only which tasks are done, in completedTaskIds, so a stopped run resumes where it left off.

      When does it become vertical slices

      plan decides in its step 3, One story or several. A story is by definition a vertical slice: something you can demo through every layer.

      01

      One story when it fits

      The work stays one story when it is one vertical slice that fits a single exec run in a fresh context with headroom, about 12 tasks.

      02

      Otherwise the fewest slices

      plan cuts the fewest stories that cover the source, none overlapping. It never cuts by layer, such as endpoint, handler and UI on their own.

      03

      Too big splits thinner

      A story that comes back OVERSIZE: is cut into thinner vertical slices.

      04

      Seams and overlaps

      Where module boundaries are strong, the work splits along them and sharedDecisions pins the interface. Stories that would touch mostly the same files are merged, except a walking skeleton: when the main flow crosses several stories, the first is its thinnest end-to-end path, and the stories that thicken it depend on it.

      Watch the names

      Two numberings share the letter S. Story IDs in plan.json are S01, S02 …, and so are the acceptance scenarios inside a FIS. In a FIS, Story-ID: S03 names the story; S01 [OC01] further down is a scenario.

      Parallel stories

      How AndThen decides what can run at once

      Only a plan directory can run stories in parallel, and only when you add --worktree. A single FIS is always built as one piece. Two skills share the decision: plan draws the dependencies when it cuts the stories, and exec-plan reads them again before every batch.

      Example plan
      StoryNameDepends on
      s01Lists have owners–
      s02Share a lists01
      s03Sort by due date–
      s04Revoke a shares02

      /andthen:exec-plan <dir>

      s01→s03→s02→s04

      One story at a time, in plan order as each becomes ready, because a shared working tree shares one test run.

      /andthen:exec-plan <dir> --worktree

      s01s03→merge→s02→merge→s04→merge

      s01 and s03 depend on nothing, so they start together, each in its own worktree. s02 waits for s01 to be merged, and s04 for s02.

      01

      plan draws the edges

      dependsOn holds causal edges only: a story depends on another only when it uses something that story produces, a contract or a decision. Stories that would touch mostly the same files are merged into one, and an interface two stories share is pinned in sharedDecisions. plan’s last line names exec-plan on the first ready story’s FIS, and each story run names the next. Running the whole directory, with or without --worktree, is your call.

      02

      exec-plan takes one wave at a time

      Before each batch it re-reads plan.json and takes the stories whose dependencies are all done. With --worktree it starts up to about five of them at once, each a fresh subagent on its own story/<id> branch in its own worktree.

      03

      The merge has the last word

      Each finished story is merged with git merge --no-ff before the next batch starts, so the stories that depend on it start from a base that has its work. A merge conflict fails the story, unless both sides only added lines to an append-only document such as Learnings. A failed story keeps its worktree, and the stories that depend on it are skipped. After each merged batch, one simplify pass covers its stories, and what they found goes into the FIS files of stories not yet started.

      Prerequisites: --worktree stops before the first story when a tracked file has uncommitted changes, or when plan.json is not committed, because a worktree holds only what was committed.

      Rules of the Core Loop

      Small steps, clean hand-offs

      01

      Every skill works standalone

      Start at whichever step fits. Requirements already written? Go straight to plan.

      02

      Each step prints the next command

      When a step finishes, the last thing it shows is the command to paste for the next one.

      03

      One fresh session per step

      Run /clear between steps. The files on disk carry the work forward, so each skill starts from the spec instead of a long chat.

      Paths and artifacts

      What can you do, and when?

      The Core Loop is the main road. AndThen has more paths beside it: a quick fix, a design detour, a bug hunt, a new domain. This tab shows which path fits your situation, what each step leaves behind, and what you can do once the pull request is merged.

      After ship

      What you can do next

      The branch is merged, and plan.json is gone unless you kept it at ship. The documents that stayed point to what comes next.

      Build the next feature

      The PRD's Out of Scope and Open Questions are a ready backlog. Start a new branch from main and pick one.

      /andthen:clarify "<the next idea>"

      Pay down tech debt

      Every deferred finding sits in docs/TECH-DEBT-BACKLOG.md with its blocker. An entry you can state in one sentence is an implement-fix.

      /andthen:implement-fix "<an entry from docs/TECH-DEBT-BACKLOG.md>"

      Act on what ship recommended

      ship writes only Learnings and the PRD's Shipped line. It recommends the rest, such as a decide run for a design change no ADR records yet.

      /andthen:decide "<the change ship named>"

      Check the outcome

      Did the feature solve the PRD's problem for its users? The outcome lens reads the PRD against what was built.

      /andthen:review --mode outcome docs/specs/<feature>/prd.md

      Triage the incoming issues

      New ideas and bugs pile up in the tracker. tracker triage labels and routes each one; you ratify every write.

      /andthen:tracker triage "the ten oldest"

      Stop for the day

      Hand off with the next focus, so tomorrow's fresh session starts from files, not memory.

      /andthen:handoff "next: <the focus>"

      Worked example

      ui-ux-design for shared lists

      The same feature as the Foundation Lab, now with its screens designed before the spec. The share dialog has real states to get right, so it earns wireframes. One dialog does not earn a design system.

      prd.md→research→wireframes→design system→plan→exec-plan→visual-validation

      Steps

      1. Research the flows, if they are unclear. The answer comes in the chat, with no file: the job to be done, two to five journeys, a sketch of the navigation, constraints and open questions. Open questions send you back to clarify.

        /andthen:ui-ux-design "research the shared-lists flows" docs/specs/let-people-share-their-lists/prd.md

      2. Wireframe every screen and state. It writes a page inventory first, then one grayscale HTML page per screen and state, then checks them at four viewports.

        /andthen:ui-ux-design "wireframe the share dialog and the member list, all states" docs/specs/let-people-share-their-lists/prd.md

      3. A design system, only for a broad surface. A whole collaboration area across many screens earns tokens and component styles. One dialog does not. Once `DESIGN.md` exists, asking it to mock up the screens builds clickable mockups from its tokens in `docs/mockups//`.

        /andthen:ui-ux-design "create a design system for the collaboration screens" docs/specs/let-people-share-their-lists/prd.md

      4. Plan from the design. ui-ux-design closes on this command. The FIS cites the wireframes, so exec-plan builds to them.

        /andthen:plan docs/specs/let-people-share-their-lists/

      5. Check the built screens. Set up the capture procedure once, then compare the built screens with the wireframes.

        /andthen:visual-validation --mode setup
        /andthen:visual-validation "share dialog and member list, mobile and desktop" docs/wireframes/shared-lists/

      What you do with them

      01

      Open docs/wireframes/shared-lists/index.html in a browser

      Every screen should be there, and every state: empty, error ("no account for that email"), already shared, loading.

      02

      Hold it against page-inventory.md

      No page skipped for looking "similar" to another. A missing state is a screen the agent will invent later.

      03

      Commit them with the PRD

      The FIS cites them while the branch builds. At ship, ship asks whether to delete the feature's wireframe folder, and recommends it once the screens are built and validated. The design system stays.

      04

      Plan from them

      The FIS names the wireframes as the asset to build against, and exec-plan builds to them instead of guessing the layout.

      05

      Validate what was built

      visual-validation lists every difference from the wireframes before its verdict. P1 and P2 findings block; P3 is reported.

      Sizing check: One field added to an existing form earns no wireframes. A dialog with real states earns wireframes. A whole surface across many screens earns a design system, and mockups once you want those screens approved in its look. An API change earns nothing from this skill.

      Worked example

      decide, architecture and spike for todo search

      A next feature for the todo app: search your own todos and those in lists shared with you. How to search is a real choice: the options sit close, one breaks a standing non-goal, and one question only running code can answer. The PRD is already in place, in docs/specs/search-todos/prd.md.

      prd.md→architecture→decide→trade-off→spike→ADR→plan

      Steps

      1. Ask for advice on the shape. architecture in advise mode answers in the chat and writes nothing. Here it routes search through the read check from ADR-002, so the todos in a shared list are found and nobody else's are. A fork worth recording goes on to decide.

        /andthen:architecture "how should todo search fit with the list access helpers, so shared lists are searched but nobody else's?"

      2. Frame the decision. decide lists the decision points and sorts them. Where access is checked is settled by ADR-002, so it is cited, not asked. How results are ranked is local to one story and left to plan. How to search binds beyond one story and no option stands out, so it gets a weighted trade-off.

        /andthen:decide "compare three options for searching todos, from docs/specs/search-todos/prd.md"

      3. Confirm the criteria before the research. The first gate: the decision context, the options and a weight per criterion. An external search engine is flagged by the one-SQLite non-goal in docs/PRODUCT.md. The floor option, a plain LIKE query on what exists, is always in the set. Adjust the weights now, because wrong weights waste the research.

      4. Spike what research cannot settle. Whether FTS5 is built into the sqlite3 module your Python ships, and how fast each option is on 10,000 todos, only running code can tell. decide hands the question to spike, which builds in its own worktree, commits on a spike/<slug> branch, removes the worktree and reports a Spike Verdict: the question, the answer with numbers, how to rerun it, and what it did not cover. The verdict folds back into the trade-off as evidence. Run on its own, the command is:

        /andthen:spike "is FTS5 in our Python's sqlite3, and how fast are LIKE and FTS5 on 10,000 todos?"

      5. Accept the recommendation and choose the ADR status. The second gate: the chosen option, what it buys over the floor, and which criteria decided it and which only broke ties. Accept it, refine the weights, or ask for a deeper look at one option. Then decide plays back the settled set and asks whether the ADR goes in as Accepted or Proposed.

      6. Keep the result, remove the spike code. Check that the verdict's numbers made it into the ADR or research.md. AndThen keeps the spike branch as evidence by default; once the result lives in the ADR, deleting it is your call. The worktree is already gone, and the branch needs -D because it was never merged.

        git worktree list
        git branch -D spike/<slug>

      7. Plan from the decision. decide closes on this command. The FIS's Architecture Decision cites the new ADR.

        /andthen:plan docs/specs/search-todos/

      The artifacts

      docs/
├── adrs/
│   └── ADR-003-<title>.md      the decision and its door type
├── DECISIONS.md                one new Current ADRs row
└── research/
    └── todo-search/
        ├── research.md         findings per option
        ├── tradeoff-matrix.md  a weighted score per criterion
        └── recommendation.md   the report: read it first
.agent_temp/spike/<slug>/       the worktree, removed at the end

      The names are examples: decide picks the ADR title and the topic folder, spike the branch name. A decision with several independent dimensions also gets design-tree.md.

      What you do with them

      01

      Read recommendation.md first

      Its Executive Summary gives the answer in one paragraph, and How to Read This Report explains the weights. Check which criteria decided it and which only broke ties.

      02

      Read the ADR's Reversal line and Alternatives

      A one-way door deserves a slow read. The floor option and the flagged external engine are both listed, each with the reason it lost.

      03

      Make the spike result durable

      The Spike Verdict's numbers and its rerun command belong in the ADR's References or in research.md. Record the decision and its evidence, never the code.

      04

      Remove the spike code

      With the verdict recorded, delete the spike/<slug> branch. Spike code is never merged or reused: the real implementation is written fresh from the FIS.

      05

      Commit the decision with the PRD

      git add docs takes the ADR, DECISIONS.md and the research folder. plan and every later skill read them through the Index.

      Sizing check: Close options on a two-way door need no trade-off: pick one. A load-bearing choice with no real alternative is one Still Current line in DECISIONS.md. A contested choice gets the trade-off and an ADR. A question only measurement settles gets a spike, and only then.

            F1 · Step 3

            Worked example: judging the warm-up diff

            Asked to “Add a short module docstring to src/app/utils.py explaining what it's for”, one agent run returned the diff below. Your agent's answer will differ; the questions stay the same.

            -"""Shared utility functions for templates and routes."""
+"""Shared utility functions for templates and routes.
+
+Due-date checks (is_overdue, is_due_today) and date formatting for display
+and for HTML date inputs (format_date, format_date_input). The route modules
+register them as Jinja template globals.
+"""

            Five questions

            1. Did it do what I asked?Check: compare it with your instruction, word for word.Here: partly. You asked for a short docstring, but one already existed, and the agent extended it without asking.
            2. Is it true?Check: test every claim against the code.Here: yes. The function names exist (grep -n "^def" src/app/utils.py), and the Jinja registration is in three route files.
            3. Did it stay in scope?Check: git diff --stat lists only the files and lines you expected.Here: yes. Only the docstring in one file changed, and no code.
            4. Does it fit its surroundings?Check: look at the code around it, its style, length and tone.Here: doubtful. Every other docstring in the file is one line, and this one runs to six.
            5. Did anything break?Check: uv run pytest.Here: no, 58 passed.

            Good

            • Everything it says is true and checked.
            • The change is small and stays in one file.
            • No logic changed, and the tests pass.
            • It kept the old line instead of overwriting it.

            Less good

            • It didn't ask. With a docstring already there, the best answer might have been “There is one already. Do you want me to extend it?”
            • It repeats the code. The function names are now in the code and in the docstring. Add a function, and the docstring is wrong unless someone remembers to update it.
            • “Short” was read generously. It is longer than every other docstring in the file.

            What I would have done: left the existing line alone, or added at most one sentence on why the module exists, not what it contains.

            The point of the exercise: you own every line, even when the agent wrote it. The five questions come back at full scale in F6, when review judges a whole feature.

            F1 · Step 7

            Worked example: right-sizing shared lists

            There are three sizes, and the entry test tells you where to start. Here is the reasoning for this lab's feature.

            The three sizes

            WorkPathStructure
            A fix you can state in one sentenceimplement-fix → shipMinimal
            One real feature[clarify →] plan → exec-plan → review --fix → shipOne FIS and a one-story plan.json
            Several featuresthe same chain, with plan <dir>A FIS per story; independent stories can run in parallel

            The entry test: if you can't list three acceptance criteria, start with clarify; otherwise start with plan.

            1. How big is the work?

            A fix in one sentence?
            No. It touches the data model, permissions and the UI.
            Several features?
            No. It is one thing: sharing a list.
            Size
            One real feature, the middle size (highlighted above).

            2. Start with clarify or plan?

            Ask yourself: can I list three testable acceptance criteria right now? All you have is one line, “Let people share their lists”. Try to write three criteria and you hit open questions at once:

            • Who can you share with: only registered users, or any email address?
            • What can the recipient do: read, change, or delete?
            • What happens when you share twice, or with yourself?
            • How and when does sharing end?

            Until those are answered, three criteria won't hold. So you start with clarify: it interviews you and writes a PRD. Had the answers existed already, say in a tracker item, you would start with plan.

            Compare: a one-sentence fix

            A bug such as “Creating a todo leaves priority empty instead of low” fits in one sentence, with one clear right answer. That is the smallest size: implement-fix, then ship, with no spec.

            Not sure which size? /andthen:now-what applies the entry test for you.

            F2 · Step 2

            Worked example: three acceptance criteria

            One way to write them, in .agent_temp/f2-my-criteria.md. Yours may differ; the point is to make the decisions on purpose, before any skill runs.

            # Share a list – my acceptance criteria

1. Share with a registered user
   Given I own the list "Groceries" and bob@example.com has an account
   When I share "Groceries" with bob@example.com
   Then Bob sees "Groceries" among his lists and can read its todos

2. The recipient can only read
   Given Bob can see my shared list "Groceries"
   When Bob tries to add, change or delete a todo in it,
        in the UI or by sending the request directly
   Then the change is refused and the list stays as it was

3. Awkward edge: an email with no account
   Given no account exists for carol@example.com
   When I share "Groceries" with carol@example.com
   Then I see "No user with that email" and nothing is shared

Out of scope: inviting people without an account, edit rights, notifications.

            What to notice

            • Each criterion is a decision. Registered users only, read-only, and a clear answer for an unknown email. Writing them forced those calls.
            • Each one is testable. Given sets up the state, When is one action, Then is something you can observe.
            • Criterion 2 covers the direct request, not just a hidden button. F6 comes back to exactly that.
            • Other edges you could pick: sharing the same list twice, sharing with yourself, revoking access.

            Keep the file. In step 5 you compare it with the PRD that clarify writes.

            F4 · Step 2

            Worked example: a hand-written FIS skeleton

            One way to write it, in .agent_temp/f4-my-fis.md, for the vertical slice share a list, view-only. Yours may differ; the format is easy, and the decisions are in the scenarios.

            # Share a list view-only – my FIS skeleton

## Intent
A household member follows another member's list as it is right now, without copying it, while only the owner can change it.

## Expected Outcomes
- [OC1] The owner shares a list with a registered user by email, and can revoke it.
- [OC2] The recipient reads the list and all its todos under "Shared with me".
- [OC3] The recipient can change nothing, in the UI or by a direct request.

## Acceptance Scenarios
S01 [OC1, OC2] Share with a registered user
  Given Alice owns "Groceries" and bob@example.com has an account
  When Alice shares "Groceries" with bob@example.com
  Then Bob sees "Groceries" under "Shared with me", marked with
       Alice's email, and can open it and read every todo

S02 [OC1] Awkward edge: an email with no account
  Given no account exists for carol@example.com
  When Alice shares "Groceries" with carol@example.com
  Then she sees "No user with that email" and no share is stored

S03 [OC3] The recipient cannot change it, even directly
  Given "Groceries" is shared with Bob
  When Bob sends PATCH /api/todos/{id}/toggle for one of its todos,
       outside the UI
  Then he gets 403 and the todo is unchanged

## What We're NOT Doing
- Leave (the recipient drops the list): a later story
- Edit rights, invitations for emails without an account, notifications
- Reordering shared lists in the sidebar

## Tasks
T1 Add ListShare as ADR-001 decides
   Verify: uv run pytest tests/test_sharing.py -k model
           (a duplicate share fails; deleting the list removes its shares)
T2 Add get_owned_list and get_readable_list (ADR-002), and switch
   every list and todo route to one of them
   Verify: grep -n "_verify_list_access" src/app/routes/todos.py finds nothing,
           and uv run pytest is green
T3 Share and revoke routes, and the Share section in list settings
   Verify: uv run pytest tests/test_sharing.py -k share (S01, S02)
T4 "Shared with me" in the sidebar, and a list view with no change controls
   for the recipient
   Verify: uv run pytest tests/test_sharing.py -k recipient (S03);
           inspect: signed in as Bob, no add field, pencil or trash icon

            What to notice

            • Each scenario names its outcome. The [OC] tags show what proves what. OC1 promises revoke, but no scenario proves it: a gap like that is what step 4 should catch.
            • S03 sends the request directly. A hidden button is not a refusal. The server has to say no, and the scenario says how you see it: 403, and the todo unchanged.
            • Every task has a Verify you can run or inspect. "It works" is not a Verify. A test name, a command or a thing to look at is.
            • The tasks lean on the ADRs. T1 and T2 follow ADR-001 and ADR-002 instead of redesigning the model or the access check.
            • Not doing is a decision too. Leave is in the PRD (FR5), but this slice parks it on purpose.

            Keep the file. In step 4 you compare it with the FIS plan writes: expect it to add the scenarios you skipped, such as revoke, sharing twice and an empty email, and a proof for every change route, not just one.

            F6 · Step 2

            Worked example: falsify one check

            In the reference run, each change route looks up the list through an owner check. Three moves, all from todo-app/:

            1. Change one line. Open src/app/routes/todos.py and find this line in update_todo:

            list_obj = get_owned_list(db, todo.list_id, user_id)

            Swap get_owned_list for get_readable_list, and save. It is already imported at the top of the file, so nothing else changes. get_owned_list returns the list only to its owner; get_readable_list also returns it to anyone it is shared with. After the swap a viewer passes the check, and the update goes through.

            2. Run the tests: uv run pytest. One test must fail:

            FAILED tests/test_sharing.py::test_recipient_change_requests_refused[update todo]
1 failed, 88 passed

            Save the file first: unsaved, the tests run the old code and stay green, which looks like a lying suite but isn't.

            3. Put the check back: git restore src/app/routes/todos.py. Then git status --short src/ prints nothing.

            Your run may name or place the check differently. Look for where a change route – update, toggle or delete – fetches the list and refuses anyone who doesn't own it. Or ask Claude: “Which line in the update route refuses a viewer? Show me, don't change it.”

            Why not just comment the check out? The route would crash, and a crash fails tests whether or not they check the right thing. A check that lets a viewer through keeps the code running, so only a test that asserts the refusal goes red.

            The agent reads a pull request or a git range and writes a walkthrough under .agent_temp/walkthrough/. Source code is not touched.
            
      
            
    
            

    
            
      
            
        
            Rules for Studio
            
        
            Look here, work there
            
      
            
      
            
        
            01
            The files are the truth
            Studio is a view of what AndThen wrote. When the view and a file disagree, the file wins: read it in your editor or with git diff.
            
        
            02
            No notes while exec-plan runs
            Send notes edits an artifact, and a FIS edited mid-run is the same as hand-editing it. Read and write notes freely, and send them after the run.
            
        
            03
            Send notes leaves a change to review
            It is the only action that edits a project file. Check it with git diff and commit it by path, like any other change, before the lab's next git status check.
            
      
            
    
            

    
            
      
            Troubleshooting
            
      
            The home page says 0 plans
            plan.json lives under docs/specs/ only between F4 and F7. Before F4 there is none yet, and ship deletes it in F7, so 0 plans is the right answer then. A plan you parked in .agent_temp/ is not shown either. If a plan should be there, check the Specs & Plans row in the Index, or start Studio with --specs-dir docs/specs.
            
      
            Models, boards and tours are empty
            Expected in the Foundation Lab. The atlas needs andthen:describe --model, event storms and context maps need andthen:architecture, and a walkthrough appears only after you produce one.
            
      
            AI actions are off
            Studio needs Claude Code 2.1.273 or later, or Codex 0.154.0 or later, on the PATH. Its startup output says which one it found. Point it at another executable with --agent claude --agent-bin <path>.
            
      
            Is my version current?
            andthen_studio --version prints the installed release. Studio never checks for updates itself: compare with the releases page, and run the install command again to update.

            Where do I set
            
        
            Where do I set…?
            
        
            Each setting AndThen honours has one place, and every skill reads it from there, so a change made once holds for every later run.
            
      
            
      
            
        
            
          
            QuestionWhereHow

            Which model runs without role agentsyour session/model in Claude Code, or the model picker in the app. Every subagent inherits it.
            
            
            How briefly Claude answers~/.claude/settings.jsonSet "outputStyle": "andthen:concise-critical" and start a new session. A project setting overrides it.
            
            
            Where a document livesCLAUDE.md, Project Document IndexMove the file and edit its Index line. Skills find documents by entry name, so keep the names.
            
            
            Which commands prove the code worksdocs/KEY_DEVELOPMENT_COMMANDS.mdEdit the fast and full rows. exec-plan runs fast per story and full on the final tree.
            
            
            Rules every session must followCLAUDE.mdAdd them under Project-Specific Guidelines and Rules, or adopt the Critical Rules section init offers.
            
            
            Which AndThen version you run~/.claude/plugins/known_marketplaces.json and installed_plugins.jsonUpdate with /plugin marketplace update andthen and /plugin update andthen@andthen, then restart. To switch branch or tag, remove the marketplace and add it again as IT-HUSET/andthen@<ref>.

            Models
            
        
            Which model does what
            
        
            AndThen never names a model in a prompt. Each skill hands work to a role: the installed role agent when there is one, else a subagent on your session's model, with judgment work kept in your session.
            
      
            
      
            
        
            oracle
            model · fableeffort · high
            Judgment you assign it, such as a design or a second opinion, and hard problems another agent hands over because they exceed its tier.
            
        
            implementer
            model · sonneteffort · high
            One medium or large unit of pinned work: building a story, writing a plan story's FIS, research that weighs sources.
            
        
            reviewer
            model · opuseffort · medium
            Every review, of any target, returning findings and a verdict.
            
        
            worker
            model · haikueffort · high
            Small, well-specified subtasks: lookups, scans, mechanical edits.
            
      
            
      
            Install and change them
            
      
              
        
            1. 01
              Check what you have
              If neither ~/.claude/agents/ nor the project's .claude/agents/ exists, every skill runs on your session's model: change that with /model in Claude Code, or with the model picker in the app. From todo-app/:
              ls ~/.claude/agents .claude/agents
              2. 
        
            2. 02
              Get the files: let init offer them
              Run init again. On a project that is already set up it takes the repair path, keeps everything you have, and offers the role agents among its extras. Choose project level to share the pins with the team, or user level for yourself.
              /andthen:init
              3. 
        
            3. 03
              Or copy the templates yourself
              They ship with the plugin. This copies all four into the project, from todo-app/ in Git Bash:
              mkdir -p .claude/agents && cp ~/.claude/plugins/cache/andthen/andthen/1.1.0/skills/init/templates/agents/claude/*.md .claude/agents/
              4. 
        
            4. 04
              Change a pin
              Open the role's file, such as .claude/agents/reviewer.md, and edit model and effort in its frontmatter. Keep name as it is: a skill asks for the role by that name.
              5. 
        
            5. 05
              Start a new session in todo-app/
              Agent definitions load when a session starts, and the project's agents apply only to sessions started in todo-app/, where its .claude/agents/ lives.
              6. 
      
            
      
            Note
            Never edit the templates inside the plugin: an update replaces them. Edit your copies, and check their pins again when the model lineup changes.

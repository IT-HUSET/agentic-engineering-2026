# Discovered Requirements: Todo App
> Status: Discovered – requires validation by team

Reverse-engineered from the code as it stands. Paths are relative to the project root. "Confidence" rates how sure the reading of the code is, not whether the behavior is desirable.

## System Overview

A single-process, server-rendered, multi-user todo web app (`pyproject.toml`: `todo-app` 0.1.0). Users register and log in with email and password, then manage several private todo lists, each holding ordered todo items with title, note, due date, priority and completion state. FastAPI routes return Jinja2 HTML pages and HTMX fragments (no JSON API); SQLAlchemy persists to a local SQLite file; Shoelace, HTMX and SortableJS load from public CDNs. The project declares itself educational and not for production: plain-text passwords and in-memory sessions (`README.md` "Educational Notice", `src/app/database.py`, `src/app/core/deps.py`). There are no admin or operator features and no background jobs; the only non-request process is the startup lifespan (`src/app/main.py`).

## Implicit Business Rules

- **RULE-D01**: Every `/api/*` endpoint requires a valid session. Without one, HTMX requests get `401` with `HX-Redirect: /login?next=/app`; other requests get `302` to `/login?next=/app`. Page routes use the requested path as `next` – Evidence: `src/app/core/deps.py` (`get_current_user_id`), `src/app/main.py` (`unauthorized_handler`), `tests/test_auth.py::test_api_requires_auth`
- **RULE-D02**: Lists are private to their owner. Every list query filters on `TodoList.user_id == <session user>`; a foreign list id behaves exactly like a missing one (`404` on the API, redirect to `/app` on the page route). There is no sharing – Evidence: `src/app/routes/todo_lists.py` (all handlers), `src/app/routes/pages.py` (`app_list_page`)
- **RULE-D03**: Todo access is authorized through the parent list: the todo is loaded by id, then its list must belong to the user, else `403` – Evidence: `src/app/routes/todos.py` (`_verify_list_access` in `get_todo`, `update_todo`, `toggle_todo`, `delete_todo`, `reorder_todo`), `tests/test_todos.py::TestTodoAccess`
- **RULE-D04**: Creating and searching todos require ownership of the target list (`404` "List not found" otherwise) – Evidence: `src/app/routes/todos.py` (`create_todo`, `search_todos`)
- **RULE-D05**: List reorder silently skips ids the user does not own or that do not exist – Evidence: `src/app/routes/todo_lists.py` (`reorder_lists`)
- **RULE-D06**: Email must be syntactically valid on both login and register (Pydantic `EmailStr` with `email-validator`). Email is unique per account (DB unique constraint plus a pre-check returning "Email already registered"). Lookup is an exact, case-sensitive string match; no normalization – Evidence: `src/app/routes/auth.py` (`EmailStr._validate`, `User.email == email`), `src/app/database.py` (`unique=True`), `tests/test_auth.py::test_register_duplicate_email`
- **RULE-D07**: Registration requires a password of at least 6 characters that equals the confirmation; there is no maximum length or complexity rule. Passwords are stored and compared in plain text – Evidence: `src/app/routes/auth.py` (`register`, `user.password != password`), `src/app/database.py` (comment "Plain text - educational only!")
- **RULE-D08**: A session is a random UUID4 with a fixed 1-hour lifetime from login (not extended by activity). The cookie is `httponly`, `samesite=lax`, `max_age=3600`, not `secure`. Expired sessions are removed lazily on lookup; all sessions are lost on restart; a user may hold several sessions at once – Evidence: `src/app/core/deps.py` (`create_session`, `get_session`, `set_session_cookie`)
- **RULE-D09**: The post-login `next` target is accepted only if it starts with `/`, does not start with `//` and contains no `://`; otherwise the user goes to `/app`. Registration always goes to `/app` – Evidence: `src/app/routes/auth.py` (`is_safe_redirect`), `tests/test_auth.py::test_login_blocks_open_redirect`
- **RULE-D10**: List name is required (non-blank after trimming) and at most 100 characters (length checked before trimming); it is stored trimmed. Description is trimmed, and blank becomes null. Color defaults to `#3b82f6` and is stored as sent, without server-side validation – Evidence: `src/app/routes/todo_lists.py` (`create_list`, `update_list`), `src/app/database.py` (`color = Column(String(7), default="#3b82f6")`)
- **RULE-D11**: Todo title is required (non-blank after trimming) and at most 200 characters (checked before trimming); stored trimmed. Note is trimmed, and blank becomes null – Evidence: `src/app/routes/todos.py` (`create_todo`, `update_todo`)
- **RULE-D12**: Priority is one of `low`, `medium`, `high`. Quick-add always sets `low`; an update with any other value is silently coerced to `low` – Evidence: `src/app/routes/todos.py` (`create_todo`, `update_todo`), `src/app/database.py` (comment `# low, medium, high`)
- **RULE-D13**: Due date is a calendar day in `YYYY-MM-DD` form. A blank value clears it; an unparseable value is ignored and the previous due date is kept. It is stored as a naive datetime at midnight – Evidence: `src/app/routes/todos.py` (`update_todo`, `datetime.strptime(due_date, "%Y-%m-%d")`)
- **RULE-D14**: A todo is overdue when it has a due date before the server's current local date and is not completed. It is due today when its due date equals the server's local date, completed or not (CSS hides the due-today style on completed rows). Time of day is ignored – Evidence: `src/app/utils.py` (`_as_date`, `is_overdue`, `is_due_today`), `tests/test_utils.py`
- **RULE-D15**: Completion is changed only by the toggle endpoint: it flips `is_completed`, sets `completed_at` to the current UTC time on completion and clears it on un-completion. The edit form (PUT) cannot change completion, position or the owning list – Evidence: `src/app/routes/todos.py` (`toggle_todo`, `update_todo` parameters)
- **RULE-D16**: The sidebar count of a list is the number of its incomplete todos – Evidence: `src/app/routes/todos.py` (`_get_list_todo_count`), `src/app/templates/partials/todo_list_item.html` (`selectattr('is_completed', 'false')`)
- **RULE-D17**: Lists are ordered by `position` per user and todos by `position` per list. A new list or todo is meant to go last, at `max(position) + 1` – Evidence: `src/app/routes/todo_lists.py` (`create_list`), `src/app/routes/todos.py` (`create_todo`), `src/app/routes/pages.py` (`order_by(... position)`); see GAP-D01 for the actual result
- **RULE-D18**: Moving a todo to a target position shifts every todo between the old and new position by one; moving to the current position is a no-op. The target is not bounds-checked – Evidence: `src/app/routes/todos.py` (`reorder_todo`), `tests/test_todos.py::test_reorder_todo_move_*`
- **RULE-D19**: Deleting a list deletes all its todos; deleting a user would delete their lists and todos. Both rely on the ORM `cascade="all, delete-orphan"`; SQLite foreign keys are not enforced. No route deletes users – Evidence: `src/app/database.py` (relationships, `ondelete="CASCADE"`), `tests/test_integration.py::test_delete_user_cascades_to_lists_and_todos`
- **RULE-D20**: Response status conventions: validation failures return the error alert with `200` so HTMX swaps it in; missing resources `404`; foreign todos `403`; database errors `500` with the generic message "Database error occurred". `DELETE` and reorder endpoints answer `404`/`403` with an empty body – Evidence: `src/app/routes/*.py`, `src/app/main.py` (`db_exception_handler`), `tests/test_todo_lists.py::test_create_list_empty_name`

## Non-Functional Characteristics

- **NFR-D01 Caching**: No server-side caching and no cache headers on responses. The client adds `Cache-Control: no-cache, no-store, must-revalidate` and `Pragma: no-cache` to every HTMX request – Evidence: `src/app/static/js/app.js` (`htmx:configRequest`)
- **NFR-D02 Rate limiting**: None, including on login and registration – Evidence: absence in `src/app/routes/auth.py`, `src/app/main.py` (no middleware)
- **NFR-D03 Error handling**: Expected failures become an inline `sl-alert` fragment; `SQLAlchemyError` maps to a `500` fragment; `401` maps to a login redirect; the client shows a generic toast on any non-2xx HTMX response – Evidence: `src/app/main.py`, `src/app/templates/partials/error.html`, `src/app/static/js/app.js`
- **NFR-D04 Logging and observability**: No server logging (no `logging`, no `print` in `src/`); only `console.error` in the browser. No health endpoint or metrics. FastAPI's default `/docs` and `/openapi.json` stay enabled – Evidence: `src/app/`, `src/app/main.py` (`FastAPI(...)` without `docs_url=None`)
- **NFR-D05 Performance**: A new SQLite connection per session (`NullPool`); no pagination of lists or todos; search is `ILIKE '%q%'`, a full scan within the list; sidebar counts lazy-load each list's todos in the template (one query per list); list reorder issues one query per id. Indexes exist on `users.email`, `(user_id, position)` and `(list_id, position)` – Evidence: `src/app/database.py`, `src/app/routes/todos.py`, `src/app/routes/todo_lists.py`, `src/app/templates/partials/todo_list_item.html`
- **NFR-D06 Security posture**: Educational only. Plain-text passwords; in-memory sessions; no CSRF tokens, so mutations rely on `SameSite=Lax`; cookie not `Secure`; Jinja2 autoescaping is on for `.html` templates; open-redirect guard on login – Evidence: `README.md`, `src/app/core/deps.py`, `src/app/routes/auth.py`
- **NFR-D07 Scalability and deployment**: Exactly one process. The in-memory session dict breaks with several workers or replicas, and every `--reload` restart logs all users out. One SQLite file, no migrations, hard-coded settings – Evidence: `src/app/core/deps.py` (`sessions`), `run.sh`, `src/app/database.py`
- **NFR-D08 Availability of the UI**: The UI needs CDN access and does not work offline – Evidence: `src/app/templates/base.html`
- **NFR-D09 Accessibility**: Form fields have `<label for>`; icon buttons carry `label` attributes; drag-and-drop has no keyboard alternative in the code – Evidence: `src/app/templates/app.html`, `src/app/templates/partials/todo_item.html`, `src/app/static/js/app.js`
- **NFR-D10 Test coverage**: 63 pytest tests across auth, lists, todos, integration journeys, Pydantic models and date helpers, run with `uv run pytest`; no coverage tool, no browser or E2E tests, so HTMX swaps, SortableJS and `app.js` are untested – Evidence: `tests/`, `pyproject.toml`, `docs/ARCHITECTURE.md` (Testing)

## Gaps & Uncertainties

- **GAP-D01**: New items do not reliably go last. Position is computed as `(max_pos or -1) + 1`; when the current maximum is `0`, `0 or -1` evaluates to `-1`, so the new item also gets position `0`. For a user who creates lists or todos through the UI, every item ends up at position `0` until a reorder rewrites them, and their order then depends on SQLite row order. Is "append at the end" the requirement? – Evidence: `src/app/routes/todo_lists.py` (`create_list`), `src/app/routes/todos.py` (`create_todo`); no test asserts positions of created items
- **GAP-D02**: The todo drag-and-drop sends the DOM index (`evt.newIndex`) while the server treats it as a `position` value. The two diverge when positions have gaps (after deletes), duplicates (GAP-D01), or when a search filter hides rows. Intended contract unclear – Evidence: `src/app/static/js/app.js` (`initTodoSortable`), `src/app/routes/todos.py` (`reorder_todo`)
- **GAP-D03**: Inline `onclick` handlers interpolate HTML-escaped titles and names into JavaScript string literals (`openEditTodoDialog('{{ todo.title | e }}', ...)`).
